---
name: vis-image
description: Discover visible UI regions from an image and optionally propose safe changes to matching specifications.
---

Invocation: `/vis-image <image-path> [all|"<query>"] [as <spec-name>] [align-by x|y|x_or_y|x_and_y] [gap <pixels>] [save]`.

If a read/discovery MCP call fails, report its code and message once in one concise sentence and stop. Do not retry, inspect or resize the image, or diagnose a different cause unless the user asks. For a failed write, never retry `create_spec` with a new idempotency key. If the response is ambiguous or times out, check `list_specs` at the exact path and read any created result with `get_spec`; reuse the same idempotency key only if a retry is necessary. If the error is a workspace conflict, refresh the workspace version and proposal, then ask for confirmation again before writing.

Call local MCP `vis_upload_image` with the image path and `mode: "discover"`. The local server reads the file and submits its bytes to authenticated remote Vispector MCP; never read, print, encode, or pass image bytes through model context. `all` requests broad visible-region discovery. A quoted query guides semantic discovery, including nested elements; it is not a pass/fail assertion. `as` selects a named target and requests a preview, but does not authorize a write. Optional `align-by` accepts `x`, `y`, `x_or_y`, or `x_and_y` and defaults to `x`; optional `gap` is an integer pixel tolerance from 0 to 1000 and defaults to 5. Forward these as `align_by` and `align_gap` to `vis_upload_image`. They guide region ordering and generated one-axis offset constraints; the saved gap is used as the tolerance by later `run_inspect` checks. Omit these arguments from inspect-mode calls.

Without `save`, show returned observations. With `as`, resolve a matching existing spec and read it using remote `get_spec`; if there is no match, show a create preview at the selected scope. Do not write either preview. With `save`, paginate all relevant `list_specs` results in the selected subtree (or the named target's scope), then read complete documents with `get_spec`. Compare by name, description, and semantic identity. Present creates, updates, unchanged items, and conflicts, including exact attribute and requirement changes. Preserve assertions, regions, and specs that were not detected; absence is never deletion authority.

For each proposed spec, preserve a non-empty existing `semantic_context` exactly. If it is missing, empty, or whitespace-only, compose a concise screen-level context from the selected regions' observed labels, descriptions, hierarchy, and relationships. Use only the regions selected for that proposal; do not infer context from unselected discoveries or from the query alone. Describe the screen or area those regions collectively represent, without turning region details into expected behavior or checks. Include the synthesized context in the preview and confirmation proposal. If no regions are selected, do not invent context; explain that context is needed before the spec can be saved.

Do not write until the user explicitly confirms the presented proposal. `save` alone is not confirmation. Apply only the confirmed subset. Before each write, read the current workspace with `list_specs` or `list_taxonomy` and use its fresh `workspace_version`; never use a version from an earlier preview or `get_project`. For `create_spec`, submit a complete Visual QA document. Each region must be an object with `region_id`, `description`, `required`, `bbox` (use `null` when unavailable), `attributes` (`texts`, `colors`, `appearance`), and `checks` (use `[]` when none). Do not send discovery summaries in the shorthand `{id, name, description}` form. Use `attentions: []` when there are none. Use one stable idempotency key for that confirmed create. After success, call `get_spec` with the returned `project_spec_id` and verify the stored `semantic_context` and every proposed region field before reporting success. If readback shows approved details missing, make one `update_spec` using only the exact approved content and the fresh workspace version, then read back again. Preserve unrelated fields and report partial failures accurately. Do not create taxonomy folders or represent observations as intentional requirements without approval. Use the backend-supported predicates only. See `docs/usage.md` and `docs/limitations.md`.
